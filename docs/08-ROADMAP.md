# 08 — Milestones and acceptance gates

One milestone per build prompt. A milestone is done when its gate passes; do not
start the next one before then. Each gate is checkable by running a command, not by
opinion.

| M | Prompt | Deliverable | Gate |
|---|---|---|---|
| M0 | `00-bootstrap.md` | repo skeleton, packaging, CI, schemas vendored, `alc --version` | `make check` green on a clean clone; `alc --version` prints; `pytest` collects ≥1 test; importing the package pulls in no third-party module except `jsonschema` (asserted by a test that inspects `sys.modules`) |
| M1 | `01-core-engine.md` | `Crossing`, `Target`, `Trigger`, seeding, redaction, json patch, `TraceRecorder`, `ChaosEngine` skeleton, vanilla adapter | a fake agent runs under `engine.run()` and produces a schema-valid `trace.jsonl`; targeting/trigger truth tables unit-tested; determinism test passes |

| M3 | `03-llm-faults.md` | all 10 LLM/prompt faults + injection corpus | message normalization round-trips losslessly; each fault's effect asserted on `FakeLLM`'s received messages; injection corpus has ≥15 payloads each with a `detect` rule |

## Sequencing rules

- M0–M4 have no framework dependency at all. If a later phase needs something from
  the core, add it to the core in that phase and update `docs/02-API.md`.
- M5 (LangGraph) comes **after** the report pipeline on purpose: the report format
  is the hard part, and it is easier to get right against fake agents than against a
  graph.
- M6 comes after M4 because the judge consumes probe output. Building the judge
  first leads to a model being asked to do the probes' job.
- M8 is not optional. The demo agent is what proves the library works and what the
  README screenshots come from.
- M10 is v0.2.0 by default and must not be started before M4: the dashboard reads the
  report and trace contracts, and building it early creates pressure to bend them
  toward what is easy to render. It may be pulled ahead of M9 if the dashboard should
  ship in 0.1.0 — in that case its CLI goes into M9's gate as well.

## Post-v0.1 backlog (do not build now)

Keep this list in `docs/08-ROADMAP.md` and add to it rather than scope-creeping a
phase.

- `pytest` plugin: `@pytest.mark.chaos(preset="tool_contract")`.
- GitHub Action that comments the suite summary on a PR (attach the M10 HTML export
  as the run artifact).
- Dashboard follow-ons, once M10 lands: a suite-level fault-coverage heatmap
  (fault kind × scenario), a run-comparison view (two runs side by side), and a
  timeline flamegraph for parallel LangGraph branches. Still read-only.
- More adapters: OpenAI Agents SDK, CrewAI, AutoGen, plain LangChain AgentExecutor.
- A JS/TS port sharing `chaos_report.schema.json`.
- **LLM record/replay cassettes (top item, D-45).** Without them no scenario against
  a real model is reproducible and users will blame the library for flake. The
  normalized-message interception point already makes it cheap: record
  `messages_hash -> response`, then `--replay CASSETTE`.
- Fault *search*: given a budget, find the minimal fault that breaks the agent
  (delta-debugging over the fault space).
- Statistical mode: N seeds per scenario, report failure probability instead of a
  boolean.
- Cost model: per-provider token pricing to fill `metrics.cost_usd`.
- Trace import: build a report from an existing OpenTelemetry / LangSmith trace so
  chaos findings and production traces share one schema.
- `must_not` policy files shared across repos (an org-wide "never leak a secret"
  baseline).
- **Validation against real agents (accepted 2026-09-04).** The `AGENT_TASK.md`
  format passed its `RUNBOOK.md` §5 read on a generated finding, but a fixture is a
  weak test of actionability: the work order was produced against an agent this
  project also wrote. Clone several real agentic repositories from GitHub, run the
  suite against them unmodified, and judge the resulting work orders on findings
  nobody designed the fixture to produce. Do this after M9, when `pip install` plus
  `alc run` works from a clean checkout, so the exercise measures the tool rather
  than the build tree.

## Release checklist (M9)

1. `CHANGELOG.md` `## 0.1.0` section written from the `## Unreleased` entries.
2. Version bumped in one place (`src/agent_loop_chaos/version.py`), read by
   `pyproject.toml` dynamically.
3. `README.md` quickstart copy-pasted into a clean venv and run end to end.
4. `LICENSE` (Apache-2.0), `NOTICE`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`
   present; `CONTRIBUTING.md` explains how to add a fault and a probe in ≤20 lines.
5. `python -m build`; `twine check dist/*`; install the wheel in a clean venv and
   run the demo suite from it. This step is not a formality: it is the only place a
   packaging or extras defect can surface, and it has caught one (D-123).
6. Git tag `vX.Y.Z`; GitHub release notes = the changelog section plus one
   `AGENT_TASK.md` example, because that artifact is the pitch.
7. README badges: CI, PyPI, Python versions, license.

Steps 5 and 6 are automated by `.github/workflows/release.yml`: pushing a `v*` tag
re-runs the whole gate at that commit, refuses a tag that disagrees with
`version.py` or has no changelog section, builds, uses the wheel from a clean venv,
and publishes via PyPI Trusted Publishing — OIDC, so no API token is stored anywhere.
`workflow_dispatch` publishes to TestPyPI for a rehearsal. The one-time PyPI-side
setup is documented at the top of the workflow.
